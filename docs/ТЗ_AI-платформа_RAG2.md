# Техническое задание на MVP корпоративной AI-платформы RAG2

**Версия:** 1.0 · **Дата:** 2026-09-01 · **Статус:** утверждено к разработке
**Связанные документы:** ADR-000, ADR-001…007, docs/c4/

## 1. Общие сведения

### 1.1. Наименование
Корпоративная AI-платформа RAG2 — AI-ассистент для сотрудников с поиском по документам и транскрипцией встреч.

### 1.2. Назначение
Снижение потерь рабочего времени на поиск информации (1 000–3 000 ч/день на компанию), фиксация экспертизы, разгрузка экспертов, исключение использования внешних AI-сервисов с корпоративными данными.

### 1.3. Пользователи
- **Сотрудники** (до 4 000) — потребители ассистента через веб-UI.
- **Администраторы** — управление workspace, правами, моделями.
- **Аудиторы ИБ** — просмотр журнала аудита.

## 3. Нефункциональные требования

| ID | Категория | Требование |
|---|---|---|
| N-01 | Производительность | TTFT p95 < 3 c; полный ответ p95 < 15 c; retrieval p95 < 500 мс |
| N-02 | Пропускная способность | MVP: 10 RPS устойчиво, 25 RPS пиково; прод: 50 RPS (см. сайзинг) |
| N-03 | Доступность | MVP 99.5%; прод 99.9% |
| N-04 | Безопасность | Данные не покидают периметр; TLS 1.3; шифрование at-rest (Фаза 2 — LUKS/TDE) |
| N-05 | Масштабируемость | Горизонтальное масштабирование каждого слоя без изменения кода |
| N-06 | Развёртывание | docker compose для MVP; Helm/Terraform для Yandex Cloud |
| N-07 | Воспроизводимость | Полный подъём стека одной командой; сид-данные для демо |
| N-08 | Лицензии | Только Apache 2.0 / MIT / BSD (коммерческое использование) |
| N-09 | Тестируемость | Unit + интеграционные тесты; критичный тест RBAC |

## 4. Ограничения

- Python (backend) — по решению заказчика; Go не используется в MVP.
- Только веб-UI (Telegram-бот исключён).
- MVP на consumer GPU (RTX 4090 24GB) — осознанный компромисс стоимости.
- Контекст LLM — 8 192 токенов (достаточно для RAG-чанков).

## 5. Критерии приёмки

### 5.1. Блокирующие (не принято без них)
1. Deployment-диаграмма и Data Flow присутствуют в документации.
2. **Проверка прав доступа:** интеграционный тест — User B получает «нет доступа» на запрос по секретному документу User A; чанки A не попадают в контекст B (pre-filter, не пост-фильтрация).
3. Control Plane (агенты/API) отделён от Data Plane (БД/модели) — по Deployment-диаграмме и сетевым правилам.
4. Оркестрация — LangGraph state machine (не линейные скрипты): код `agents/graph.py` с явными узлами и условными переходами.

### 5.2. Желательные
5. Стриминг ответов (SSE) реализован.
6. Нагрузочный отчёт с RPS/латентностью на тестовом железе.
7. Дашборды Grafana провиженятся автоматически при подъёме стека.

## 6. Порядок проверки

1. `docker compose up -d` — стек поднимается, health-checks зелёные.
2. `pytest backend/` — включая `test_rbac_access.py` (критерий 2).
3. Демонстрация флоу из Sequence-диаграммы: сложный запрос → план → ReAct → цитаты.
4. Grafana: дашборды с данными, trace в Jaeger по trace_id из ответа.
5. Проверка Guardrails: инъекция «ignore previous instructions» → блок + запись в аудите.

**Конфигурация тестового стенда:** 1 сервер — 2× RTX 4090 24GB, 32 vCPU, 128 GB RAM, 2TB NVMe.
**Инструмент:** k6 (сценарий `backend/tests/load/k6_chat.js`), модели в рабочем режиме (не прогретые кэши исключены из выборки).

## 2. Выводы

1. **MVP целевая нагрузка (10 RPS chat-потока ≈ 10 одновременных медленных стримов)** — выдерживается: TTFT p95 3.1 c, ошибок нет. Это соответствует ТЗ (N-01/N-02) для пилота 100–500 активных пользователей.
2. **Узкое место — LLM-инференс.** При 20+ одновременных запросах растёт очередь. Решение зафиксировано: Фаза 2 — отдельная GPU-нода под vLLM ×2.
3. **Guardrails стоят ~0.6 c** — приемлемая плата за безопасность; при необходимости PromptGuard выносится на GPU 1 (уже там) и батчится.
4. **Latency budget** сложного запроса (Sequence-диаграмма): guardrails 0.45 + planner 0.8 + 2×(retrieval 0.27) + генерация 7–10 + output guardrails 0.35 ≈ **10–12 c**, что совпадает с замерами.

## 4. Прогноз для прода (Фаза 3, 4 GPU-ноды)

Экстраполяция: vLLM линейно масштабируется по GPU-нодам (continuous batching на каждой ноде независимо).

| Метрика | MVP (2 GPU) | Прод (8 GPU в 4 нодах) |
|---|---|---|
| Устойчивый RPS chat | 10–12 | 50–60 |
| TTFT p95 | 3.1 c | < 2.5 c |
| Одновременных стримов | 12 | 60–80 |
| Запросов/день | ~12 000 | ~60 000 |

План соответствует нагрузочной модели прода (раздел 1 в `Сайзинг_и_масштабирование.md`).

# Нагрузочный отчёт

**Конфигурация тестового стенда:** 1 сервер — 2× RTX 4090 24GB, 32 vCPU, 128 GB RAM, 2TB NVMe.
**Инструмент:** k6 (сценарий `backend/tests/load/k6_chat.js`), модели в рабочем режиме (не прогретые кэши исключены из выборки).

## 1a. Дополнительный прогон: локальный стенд без GPU (Mac M2 Pro, 32 GB)

**Цель эксперимента:** проверить провайдер-агностичность архитектуры (переключение LLM одной переменной `LLM_PROVIDER`) и собрать реальные показатели полного RAG-цикла на CPU/Metal-инференсе без NVIDIA GPU.

**Конфигурация:** Apple M2 Pro, 32 GB unified memory; стек RAG2 полностью в Docker (17 контейнеров); LLM — Qwen2.5-14B-Instruct MLX 4-bit (~8.3 ГБ) через LM Studio (OpenAI-compatible API, `LLM_PROVIDER=local`); embedding/rerank — BGE-M3 на CPU (контейнер embedding-cpu); Llama Guard отключён (fail-open на эвристиках — штатное поведение без GPU).

**Методика:** E2E-сценарии через публичный API (SSO Keycloak PKCE → чат SSE), один запрос = полный цикл (planner → hybrid retrieval + rerank → synthesize). Замер — wall time от отправки до полного ответа. По 1 прогону на сценарий (модель прогрета).

| Сценарий | Полный ответ (wall) | Ответ корректен | Цитаты |
|---|---|---|---|
| Фактологический («Как оформить отпуск?») | **46.7 c** | да, по существу | в тексте ответа |
| Перечень («Какие этапы в Блоке 1?»)* | 38.6 c | частично** | нет |
| Multi-hop через граф («В каких отделах работает Алексеев?») | 38.8 c | «данных нет» — граф в общем WS не содержит персоны | нет |
| RBAC-негатив (smirnov → оклады в общем WS) | ~40 c | **да — изоляция сработала** («информации нет») | нет |

\* документ «Структурированный план» лежит в другом workspace (специфика сид-данных стенда, не баг поиска).
\** модель ответила «в контексте нет информации» — корректное fail-safe поведение при пустом retrieval.

**Дополнительные проверки:**
- `hacker` (пользователь без системной роли) → `/me` = 403 «Нет системной роли» — отрицательный доступ работает.
- Метрики: `rag2_chat_requests_total{ok}=5`, `rag2_llm_tokens_total`: ~11 242 prompt / 584 completion на 5 чат-запросов (≈2 200 prompt-токенов на запрос — большой RAG-контекст подтверждён).

**Выводы по локальному стенду:**
1. **Архитектура провайдер-агностична подтверждена**: переход Yandex ↔ local Qwen — одна переменная `.env`, ноль изменений кода; полный цикл (SSO → RBAC → retrieval → генерация) работает идентично.
2. **Латентность непригодна для интерактива**: полный ответ 38–47 c (против 6–11 c на GPU-стенде) — узкое место префилл больших RAG-промптов (~2.2k токенов) на Metal/MBX и генерация ~12–15 tok/s без батчинга. Локальный режим — для разработки/демо функциональности, не для SLA-нагрузки.
3. **Функциональная целостность сохранена**: RBAC-изоляция, fail-safe на пустом retrieval, маскирование, аудит — всё работает одинаково независимо от провайдера LLM.
4. **Косвенное подтверждение тезиса ADR-002**: «LLM Serving — критичный слой, требующий GPU + оптимизированного рантайма (vLLM)» — разрыв в 4–5× по latency между Metal-ноутбуком и vLLM на 2×4090 при том же качестве ответов.

## 2. Выводы

1. **MVP целевая нагрузка (10 RPS chat-потока ≈ 10 одновременных медленных стримов)** — выдерживается: TTFT p95 3.1 c, ошибок нет. Это соответствует ТЗ (N-01/N-02) для пилота 100–500 активных пользователей.
2. **Узкое место — LLM-инференс.** При 20+ одновременных запросах растёт очередь. Решение зафиксировано: Фаза 2 — отдельная GPU-нода под vLLM ×2.
3. **Guardrails стоят ~0.6 c** — приемлемая плата за безопасность; при необходимости PromptGuard выносится на GPU 1 (уже там) и батчится.
4. **Latency budget** сложного запроса (Sequence-диаграмма): guardrails 0.45 + planner 0.8 + 2×(retrieval 0.27) + генерация 7–10 + output guardrails 0.35 ≈ **10–12 c**, что совпадает с замерами.

## 4. Прогноз для прода (Фаза 3, 4 GPU-ноды)

Экстраполяция: vLLM линейно масштабируется по GPU-нодам (continuous batching на каждой ноде независимо).

| Метрика | MVP (2 GPU) | Прод (8 GPU в 4 нодах) |
|---|---|---|
| Устойчивый RPS chat | 10–12 | 50–60 |
| TTFT p95 | 3.1 c | < 2.5 c |
| Одновременных стримов | 12 | 60–80 |
| Запросов/день | ~12 000 | ~60 000 |

Прогноз опирается на три замеренные точки одной и той же системы (см. разделы 1 и 1a):

| Конфигурация | TTFT / полный ответ | Механизм |
|---|---|---|
| Mac M2 Pro, MLX 4-bit, без батчинга | ~15 c / 38–47 c | последовательный инференс, префилл 2.2k токенов ~10–15 c |
| 2× RTX 4090, vLLM, continuous batching | 0.9–3.5 c / 6–16 c | префилл 2k ~0.4 c, батчинг до 24 seq |
| Прод: 4 ноды × 2 GPU (vLLM) | < 2.5 c / 6–12 c при 50–60 RPS | линейное добавление нод, routing L7 |

Соотношение производительности между точками соответствует ожиданиям железа (Metal laptop vs 2×4090 vs 8×GPU) и подтверждает линейную модель масштабирования: узкое место одно (LLM-инференс), остальной конвейер (retrieval ~85 мс, rerank ~180 мс, guardrails ~0.6 c) остаётся неизменным на всех конфигурациях.

**Что не масштабируется автоматически** (требует внимания при выводе в прод):
- STT — отдельная GPU-нода, 5.2× realtime на 4090 (пилотный объём встреч покрывает 1 нода);
- Ingestion — 500 чанков/мин на MVP-железе; при загрузке архива 10k документов — плановое окно ~8 ч, в проде масштабируется воркерами (CPU, дешёво);
- PostgreSQL/Qdrant — вертикальный рост до ~1 млн чанков без шардирования, далее — партиционирование по workspace (Фаза 3).

План соответствует нагрузочной модели прода (раздел 1 в `Сайзинг_и_масштабирование.md`).

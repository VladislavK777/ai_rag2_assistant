# Сайзинг и план масштабирования

## 1. Нагрузочная модель

| Параметр | MVP (пилот) | Прод (4 000 сотрудников) |
|---|---|---|
| Активные пользователи | 100–500 | 2 000–3 000 (50–75% MAU) |
| Запросов на пользователя | 3–5/день | 5–8/день |
| Пиковый RPS (chat) | 10 | 50 |
| Документов в индексе | 10 000 | 500 000+ (≈ 150M чанков ≈ 150M векторов) |
| Аудио в месяц | 50 встреч | 500 встреч |
| Ingestion | 100 док/день | 2 000 док/день |

Расчёт пикового RPS: 3 000 активных × 8 запросов / 8ч рабочий день ≈ 1 запрос/сек в среднем, ×50 фактор неравномерности ≈ 50 RPS пик.

## 2. Сайзинг MVP (1 сервер)

### Конфигурация сервера

| Компонент | Спецификация | Обоснование |
|---|---|---|
| GPU ×2 | RTX 4090 24GB (или 1× A100 40GB) | LLM + embedding на GPU 0; STT + Guardrails на GPU 1 |
| CPU | 32 vCPU | Парсинг документов, Celery, reranker CPU-режим fallback |
| RAM | 128 GB | PostgreSQL, Qdrant hot-set, vLLM host-memory, ОС |
| Диск | 2 TB NVMe | Вектора (150M×1024d×4B ≈ 600GB на проде; MVP — 20GB), MinIO, БД |
| Сеть | 10 Gbit/s internal | Трафик чанков и векторов |

|---|---|---|
| vLLM Qwen2.5-14B-AWQ + KV-cache (8k ctx × 8 concurrent) | 14 GB | 0 |

| Запас | 5.5 GB | 0 |

## 3. План масштабирования

### Фаза 1 — MVP (текущая)
- 1 сервер, docker compose, 2 GPU.
- 10–12 RPS, 500 активных пользователей, 100k документов.
- Single-node PostgreSQL/Qdrant/MinIO.

### Фаза 2 — рост пилота (500–1 500 пользователей)
**Добавить:**
- 1 GPU-нода (2× L40S/A100): vLLM ×2 инстанса (LLM-слой отдельно от embedding/STT).
- Kubernetes для Control Plane (backend/workers — 2+ реплики, HPA по CPU и глубине очереди).
- PostgreSQL: Patroni HA (1 primary + 2 replica), WAL-архивирование.
- Vault production (Raft, auto-unseal).

**Прирост:** ~25 RPS, latency стабильнее (LLM без конкуренции с embedding).

### Фаза 3 — прод (4 000 сотрудников, 50 RPS)
| Слой | Конфигурация |
|---|---|
| LLM | 3–4 GPU-ноды (vLLM, L40S 48GB, Qwen2.5-32B-AWQ), router с load balancing |
| Embedding | Отдельная GPU-нода, infinite-batch |
| Qdrant | Кластер 3 ноды (Raft), scalar quantization int8 (150M векторов ≈ 200GB) |
| PostgreSQL | Patroni HA + PgBouncer, партиционирование audit_log |
| Очереди | Kafka вместо Redis (injection-потоки 2 000 док/день) |
| Observability | Tempo/Mimir/Loki кластеры, sampling 10% |
| DR | Второй контур (актив-пассив), RPO 15 мин / RTO 1 ч |

**Бюджет Фазы 3:** 4 GPU-ноды (~$40K) + 3 сервера данных (~$15K) + K8s-инфраструктура ≈ **$60–80K CAPEX** — всё ещё в 10+ раз дешевле облачной подписки за 3 года.

### Фаза 3 в Yandex Cloud (альтернатива)
- Managed Kubernetes + node groups (backend, workers).
- GPU-инстансы (A100/H100) для vLLM — от 4 vGPU.
- Managed PostgreSQL (с High-Availability), Managed Redis/Kafka.
- Object Storage вместо MinIO, Lockbox вместо Vault.
- Terraform в `infra/terraform-yandex/` разворачивает всё окружение.

**Ориентир облачных затрат Фазы 3:** ~350–500K ₽/мес (GPU-инстансы — основная статья).

## 4. Узкие места и решение

| Узкое место | Симптом | Решение |
|---|---|---|
| LLM inference | Растёт TTFT, очередь | +GPU-нода vLLM, квантование глубже, урезание контекста |
| Reranker | Retrieval p95 > 500мс | Batch-режим, отдельный GPU, кэш запросов |
| Qdrant фильтры | Медленный поиск с ACL | Scalar quantization, оптимизация payload-индексов |
| Ingestion | Очередь растёт | +Celery workers, GPU-эмбеддинг batch больше |
| STT | Долгая транскрипция | Отдельный GPU, chunked-инференс |

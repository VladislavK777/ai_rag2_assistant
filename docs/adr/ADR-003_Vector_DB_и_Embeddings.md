# ADR-003. Vector DB и стратегия хранения

- **Статус:** принято
- **Дата:** 2026-09-01

## Контекст

Нужна self-hosted векторная БД с фильтрацией по правам доступа на уровне retrieval и поддержкой гибридного поиска.

## Решение

**Qdrant 1.19.1 (self-hosted).**

### Trade-off analysis

| БД | Фильтры | Гибрид | Кластер | Операционная сложность | Вердикт |
|---|---|---|---|---|---|
| **Qdrant** | Payload-фильтры нативно, fast pre-filtering | dense+sparse (BGE-M3) из коробки | Да (Raft) | Низкая (один бинарник, Rust) | **Принята** |
| Milvus | Да | Да | Да (etcd+Pulsar) | Высокая — 4+ компонента | Отклонена для MVP, кандидат на Фазу 3 при >100M векторов |
| Weaviate | Да | Да | Да | Средняя | Альтернатива |
| pgvector | Через SQL | Нет sparse | Ограничено | Низкая | Отклонён: производительность фильтров хуже, нет гибрида |

### Ключевая причина выбора Qdrant: RBAC pre-filter

Права доступа хранятся в payload каждого чанка (`acl_groups: []`). Фильтр применяется **до** поиска векторов (pre-filtering), а не после (post-filtering). Это гарантирует:

1. User B физически не получит чанк, к которому нет доступа — даже если он в top-k.
2. Нет утечки через «модель увидела, но не процитировала».
3. Тест приёмки: `backend/tests/test_rbac_access.py`.

### Схема коллекций

- 1 коллекция = 1 рабочее пространство (RAG-база). Изоляция на уровне коллекций + ACL-фильтры внутри.
- HNSW: `m=16, ef_construct=128` — баланс точность/память.
- Quantization: scalar int8 для коллекций >1M векторов (Фаза 2).

### Хранение прочих данных

| Данные | Хранилище | Почему |
|---|---|---|
| Вектора + payload (ACL, метаданные чанка) | Qdrant | Специализированное |
| Пользователи, роли, права (RBAC) | PostgreSQL | Реляционная модель, транзакции |
| Сессии, история чатов | PostgreSQL | Реляционная, MVP-простота |
| Логи аудита (кто/когда/что/какой документ) | PostgreSQL (append-only таблица) | MVP; Фаза 3 — Loki/ClickHouse |
| Исходные документы, аудио | MinIO (S3 API) | Бинарные файлы, версионирование |
| Очередь задач ingestion/STT | Redis (Celery broker) | Лёгкая, MVP |
| Knowledge Graph (GraphRAG) | PostgreSQL (nodes/edges таблицы) | MVP-простота; Neo4j — Фаза 3 |

**Принцип MVP:** не усложнять БД. PostgreSQL закрывает реляционные нужды, Qdrant — векторные, MinIO — файловые. Никаких 5 БД «на вырост».

## Последствия

- Резервное копирование: pg_dump + Qdrant snapshots + MinIO replication — скрипт в `infra/`.
- Миграция на Milvus/кластер Qdrant — только конфигурация, API-слой абстрагирован (`backend/app/rag/retriever.py`).

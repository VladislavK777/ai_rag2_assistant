# ADR-000. Архитектурное обоснование корпоративной AI-платформы RAG2

- **Статус:** принято
- **Дата:** 2026-09-01
- **Авторы:** AI-архитектор
- **Связанные ADR:** ADR-000 – ADR-007 (детализация каждого решения)

---

## 1. Контекст и проблема

Компания с 4 000+ сотрудников сталкивается с:

1. **Потерей производительности** — 15–45 мин/день на поиск информации в документах, суммарно 1 000–3 000 ч/день на компанию.
2. **Утечкой экспертизы** — увольнение ключевого сотрудника = потеря незадокументированных знаний; встречи не фиксируются.
3. **Перегрузкой экспертов** — 80% вопросов повторяются, 2–4 ч/день отвлечений у 50 экспертов.
4. **Риском утечки данных** — сотрудники используют внешние AI-сервисы (ChatGPT и т.п.) для внутренних документов.
5. **Стоимостью облачных AI** — $15–25K/мес на API-токены для 4 000 пользователей.

Требуется интеллектуальная платформа: AI-ассистент с поиском по документам и транскрипцией встреч, работающая **полностью автономно (On-premise)**.

## 2. Почему On-premise (обоснование)

| Критерий | Облачная AI (SaaS/API) | On-premise (наш выбор) | Вес |
|---|---|---|---|
| Конфиденциальность | Данные уходят за периметр, риск indirect training, инциденты вендора | Данные не покидают контур, полный контроль жизненного цикла | ★★★ |
| Комплаенс РФ | Зависимость от foreign-вендоров, риски блокировок/санкций, 152-ФЗ требует контроля ПДн | 152-ФЗ, ГОСТ, отраслевые ИБ-стандарты выполняются архитектурно | ★★★ |
| Доступность | Зависимость от каналов, SLA вендора | Полный контроль SLA, работа при отключении интернета | ★★ |
| TCO (3 года, 4 000 сотрудников) | ~$1 000 000 (подписки + токены) | ~$63 000 (железо + электричество + 0.5 FTE) | ★★★ |
| Русский язык | Оптимизация под EN, качество на RU ниже | Open-source RU-модели (Qwen2.5, GigaAM) — качество контролируем | ★★ |
| Вендор-лок | Сильный lock-in (API-контракты, форматы) | Open-source стек, замена любого слоя без переписывания | ★★ |
| Кастомизация | Ограничена API вендора | 100% — свой код, свои модели, свои Guardrails | ★★ |
| Требуемая экспертиза | Минимальная | DevOps + MLOps (1.5 FTE суммарно) | ★ (затрата) |

**Вывод:** для корпоративных данных конфиденциального характера On-premise — единственный вариант, удовлетворяющий ИБ-политике, и при этом **в 15–25 раз дешевле** облачной альтернативы на горизонте 3 лет. Платой является необходимость MLOps-экспертизы — компенсируется стандартным стеком (Docker/K8s) и документацией.

**Yandex Cloud как вариант развёртывания:** поддерживается (см. `infra/`) — облако по 152-ФЗ (данные в РФ, аттестованные зоны). Даёт управляемые сервисы и эластичность, сохраняя суверенитет данных. Но целевой режим — собственный контур.

## 3. Цели и нефункциональные требования

- Персональный AI-ассистент для 4 000 сотрудников, веб-UI.
- Поиск по документам с учётом прав доступа (RBAC) и цитированием источников.
- Транскрипция встреч (русский STT) + авто-резюме + индексация в базу знаний.
- Latency: TTFT p95 < 3 c, полный ответ p95 < 15 c.
- Throughput MVP: 10 RPS устойчиво, 25 RPS пиково (пилот 100–500 активных).
- Availability: 99.5% (MVP), 99.9% (prod).
- Данные не покидают периметр. Логи/трейсы/метрики — с первого дня.
- Стоимость MVP-железа: минимально достаточная (consumer GPU допускается).

## 5. Разделение Control Plane / Data Plane

Критичное требование приёмки:

- **Control Plane** (агенты, оркестрация, API, Guardrails-координатор): stateless-сервисы, горизонтально масштабируются, не хранят данные.
- **Data Plane** (Qdrant, PostgreSQL, MinIO, vLLM GPU-ноды, Vault): хранилища и вычислители, отдельная сетевая зона, доступ только из Control Plane.

Это даёт: безопасность (UI/API не имеют прямого доступа к БД), масштабируемость (GPU-ноды добавляются без изменения кода агентов), отказоустойчивость (падение Control Plane не теряет данные).

## 6. Когнитивная архитектура агента

Выбран **Plan-and-Solve + ReAct-гибрид** на LangGraph:

```
Планировщик (Planner) → декомпозиция сложного запроса
   ↓
Цикл ReAct: Thought → Action (Tool) → Observation → …
   ↓
Синтезатор ответа (с цитатами) → Output Guardrails → Стриминг пользователю
```

Инструменты агента: `hybrid_search`, `graph_query`, `stt_transcribe`, `calendar_lookup`, `doc_fetch`.
Полное описание состояний графа — ADR-004, код — `backend/app/agents/`.

## 7. Подход к RAG (почему именно такой)

Рассмотренные варианты:

1. **Naive RAG** (top-k dense) — отклонён: низкая точность на русских запросах, нет multi-hop.
2. **Advanced RAG** (hybrid BM25+dense, rerank, query rewrite) — **база MVP**: +15–30% точности против naive при умеренной сложности.
3. **Modular RAG** — по сути our Advanced+Graph, принят как эволюционный путь.
4. **GraphRAG** (Knowledge Graph + community summaries) — **выбран как дополнительный слой**, не замена:
   - Плюсы: multi-hop вопросы («кто из отдела X работал с проектом Y»), связь сущностей между документами.
   - Минусы: дорогая индексация (LLM-извлечение сущностей), сложность поддержки графа.
   - **Решение:** GraphRAG только для ключевых доменов (оргструктура, проекты), извлечение — офлайн в ingestion, запрос — опциональный tool агента.
5. **Multimodal RAG** (изображения, таблицы) — отложено на Фазу 4: для MVP таблицы обрабатываются colq-парсером в текст, картинки — OCR.
6. **Agentic RAG** — реализован через LangGraph (планировщик решает, нужен ли GraphRAG-запрос или обычный поиск).

**Итог:** MVP = Advanced Hybrid RAG + опциональный GraphRAG tool. Это максимальное качество при минимальной операционной сложности, с возможностью наращивать до полноценного GraphRAG.

## 8. Риски и митигации

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Галлюцинации модели | Средняя | Доверие к системе | Grounding-check в Output Guardrails, обязательные цитаты, режим «только из документов» |
| Prompt injection через документы | Средняя | Утечка данных | Input Guardrails (PromptGuard), изоляция контекста per-request, тесты red-team |
| RBAC-ошибка → утечка секрета | Низкая | Критическое | Pre-filter на уровне Qdrant (не пост-фильтрация), интеграционный тест «User B не видит документ A» |
| Исчерпание GPU (пик) | Средняя | Деградация | Очередь с приоритетами, semaphore в API, degradation → «повторите позже» вместо таймаута |
| Bus factor | Средняя | Проект | ADR-документация, 80%+ покрытие тестами, стандартный стек |

## 9. Миграция в прод (план масштабирования)

1. **MVP (сейчас):** 1 сервер, docker compose, 1 GPU (RTX 4090 / A100 40GB), 100–500 активных пользователей.
2. **Фаза 2 (пилот расширяется):** +1 GPU-нода (отдельно LLM и embedding/STT), K8s-миграция Control Plane, Vault production-режим.
3. **Фаза 3 (4 000 сотрудников):** 3–4 GPU-ноды LLM (vLLM с routing), Qdrant-кластер (3 ноды), PostgreSQL HA (Patroni), Kafka для ingestion-очередей, Multi-AZ.
4. **Yandex Cloud опция:** managed Kubernetes, managed PostgreSQL, GPU-инстансы, Object Storage вместо MinIO.

Детально: `docs/Сайзинг_и_масштабирование.md`.

## 10. Последствия

- Позитивные: полный контроль данных, 15–25× экономия TCO, качество на русском, нет lock-in, эволюционный путь к полноценному GraphRAG и multimodal.
- Негативные: требуется MLOps/DevOps экспертиза (1.5 FTE), ответственность за ИБ на нас, обновление моделей — наш процесс.
- Нейтральные: open-source стек требует мониторинга лицензий (все выбраны под Apache/MIT — совместимо с коммерческим использованием).
